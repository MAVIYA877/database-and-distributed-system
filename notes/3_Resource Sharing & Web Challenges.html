3.1 RESOURCE SHARING

Why distributed systems exist

A distributed system allows multiple users or processes to access shared resources — instead of every user needing their own private copy of everything.

Think of your bootcamp project, SkillHub LMS: hundreds of students hit the same server, the same course database, and the same file storage — at the same time. That sharing is what makes the system distributed, and it's also where every hard problem in this hour comes from.

3.3 RESOURCE SHARING PROBLEMS
PROBLEM 2 — RESOURCE FAILURE

What happens if the database server crashes?

💥 The failure

Every service that depends on that one database — Service A, B, and C — instantly loses the ability to read or write customer data. One crash, three outages.

🎯 What students should ask

Is there a backup or replica? Do requests queue and retry, or fail immediately? Does the whole application go down, or just the feature that needed data?

This is why real systems don't rely on a single point of failure — they use replication, failover databases, and retries instead of hoping the server never goes down.

3.3 RESOURCE SHARING PROBLEMS
PROBLEM 3 — RESOURCE CONTENTION

10,000 users want the same resource — simultaneously

Imagine SkillHub LMS opens registration for a free workshop, and 10,000 students click "Enroll" in the same second. They're all fighting over the same seats, the same server threads, and the same database rows.

🐌 Slower responses

Every request waits longer as the resource queues up.

🔒 Locking

The database may lock rows to prevent conflicting writes, blocking other requests.

💣 Overload

Without limits, the server can run out of memory or connections entirely.

PROBLEM 4 — CONSISTENCY

Two servers, two different answers

This happens when data is copied or cached across multiple servers and one of them hasn't received the latest update yet. Distributed systems must decide: do we wait for every copy to agree (strong consistency), or accept a short delay before they catch up (eventual consistency)?

3.5 SIMPLE LOAD BALANCER SIMULATION

Round-robin load balancer in Java

LoadBalancer.java 
class Server {

    private String name;

    public Server(String name) {
        this.name = name;
    }

    public void handle(String request) {
        System.out.println(name + " handled " + request);
    }
}

public class LoadBalancer {

    private Server[] servers;
    private int current = 0;

    public LoadBalancer(Server[] servers) {
        this.servers = servers;
    }

    public void sendRequest(String request) {
        servers[current].handle(request);
        current = (current + 1) % servers.length;
    }

    public static void main(String[] args) {
        Server[] servers = {
                new Server("Server-1"),
                new Server("Server-2"),
                new Server("Server-3")
        };

        LoadBalancer loadBalancer = new LoadBalancer(servers);

        for (int i = 1; i <= 10; i++) {
            loadBalancer.sendRequest("Request-" + i);
        }
    }
}
3.5 SIMPLE LOAD BALANCER SIMULATION

How the round-robin logic works

Server classServer just knows its own name and prints which request it handled — a stand-in for a real backend instance.
current = 0The load balancer keeps a pointer, current, to remember which server should get the next request.
sendRequest()Hands the request to servers[current], then moves the pointer forward.
% servers.lengthThe modulo operator wraps the pointer back to 0 after the last server — this is the entire round-robin trick.
for loop (10x)Ten requests are fired, cycling evenly across all three servers.

Expected output

Server-1 handled Request-1
Server-2 handled Request-2
Server-3 handled Request-3
Server-1 handled Request-4
...
